# 03 · 架构设计

## 1. 目标与非目标

**目标**
1. 原始层不可变：导出包解压后按 sha256 落盘，程序永不改写；索引层可从原始层完整重建。
2. 多来源统一：网页导出包与本地 Agent 日志用同一套归一化模型，UI 上只体现「来源徽标 + 时间」。
3. 重复导入安全：同一份包导入两次 = 无副作用；多次导出 = 自动合并 + 差异报告。
4. 多媒体一等公民：图片/音频/视频/PDF/代码附件可预览、可去重、可导出。
5. 本地优先：默认零出网；所有能力（除显式开启的模型调用）离线可用。

**非目标（v1 明确不做）**
- 不做登录态抓取 / 逆向私有 API（合规红线）。
- 不做云端同步与多端实时协作。
- 不做「替代 provider 客户端」的在线对话（那是 Chatbox/LobeChat 的领域）。
- 不追求完整支持 30+ Agent 格式（v1 六个来源，v2 按 backlog 扩）。

**关键定位：以 CLI 为绝对核心，桌面 UI 采用 Flutter (Dart) 原生编译 Windows 端，与 `Chatea` 共用同一套风格外壳。**

```
Flutter Windows App (ui_win.exe) ──spawn/connect──▶ sm serve (Node 24, 127.0.0.1:随机端口, 一次性 token)
```

理由：
1. **彻底避开 WebView2 与 Electron 的坑**：WebView2 存在宿主环境兼容性与长列表渲染性能问题，Electron 则过于臃肿（150MB+）；采用 Flutter 原生编译 Windows 桌面端（`flutter build windows`），滚动与帧率稳定可控。
2. **与 `Chatea` 复用同一套风格外壳與组件**：两个项目的桌面端同为 Flutter (Dart)，可直接共用同一套窗口设计风格、OCA Dart 数据模型、Markdown/LaTeX/代码高亮渲染、以及会话树分支切换组件。
3. **CLI 承担 100% 核心重活**：解析 GB 级 zstd/JSON、流式解压、SQLite FTS5 双索引等重 IO 任务留在 TS/Node 的 `sm` 核心进程中，CLI 可完全独立运行，Flutter 端只做干净轻量的本地视图外壳。

## 3. 技术选型

### 3.1 呈现层与 Windows 桌面外壳

| 方案 | 体积 | 兼容性与性能 | 协同收益 | 结论 |
|---|---|---|---|---|
| **CLI 核心 + Flutter (Dart) Windows 桌面端** | ~25–45 MB | 自带渲染引擎，无宿主兼容问题，长列表帧率稳定 | **与 `Chatea` 复用同一套 Dart 外壳风格与消息树组件** | **✅ v1 采用** |
| WebView2 / Tauri 壳 | ~15 MB | 依赖系统 WebView2 版本，兼容性与长列表性能不佳 | 需另写一套桌面前端 | 弃用 |
| Electron 跨平台重外壳 | ~150 MB | 内存占用高、体积臃肿 | 无 | 弃用 |

> 选型逻辑：本项目 85% 的核心价值在**适配器、查重校验流水线与 CLI** 上。桌面 UI 采用与 `Chatea` 同源的 **Flutter (Dart)** 仅构建 Windows 端（`flutter build windows`），既解决了 WebView2 兼容性与性能短板，又让两个项目共享同一套桌面视觉外壳与组件。

### 3.2 运行时与存储

| 关注点 | 选择 | 理由 |
|---|---|---|
| 核心运行时 | **Node 24 LTS** | 内置 `node:sqlite`、`zlib.zstd*`、`crc32`；流式 IO 成熟 |
| SQLite 驱动 | **better-sqlite3**（同步 API） | FTS5 必定编入、可 `loadExtension`（未来 `sqlite-vec`）、性能最好；纯本机单进程，同步 API 反而更简单 |
| zstd | 单帧用 `zlib.zstdDecompressSync`，**多帧/未知用 `fzstd`** | 实测 DSH 多帧会让内置 API 抛错 |
| ZIP | `yauzl`（流式读取，不整包入内存） | 导出包可达数 GB |
| 大 JSON | `stream-json` 增量数组解析 | `JSON.parse` 300 MB → 1.5 GB RSS |
| 魔数嗅探 | `file-type` | `.dat` 无扩展名 |
| 缩略图/转码 | `sharp`（图片）、`ffprobe` 可选（音视频时长） | 不引入 ffmpeg 全量依赖，时长缺失可降级 |
| 本地 API | `hono` | 轻、快、TS 原生，向本地 Flutter UI 提供 JSON/SSE 接口 |
| 桌面 UI | **Flutter (Dart，Windows 端)** | Riverpod + `super_sliver_list`（虚拟长列表）+ `gpt_markdown`/`flutter_math_fork`/`re_highlight`（与 `Chatea` 共用风格外壳） |

### 3.3 检索

SQLite FTS5 实测结论（Node 24 / SQLite 3.51）：

| tokenizer | `会话管理` | `会话` | `管理器` | `session` |
|---|---|---|---|---|
| `unicode61` | 0 | 0 | 0 | ✅ |
| `trigram` | ✅ | ❌(2字) | ✅ | ✅ |

→ **双索引 + 查询路由**：

- `item_fts_uni`：`tokenize='unicode61 remove_diacritics 2'` + `porter`，服务英文/拉丁词干。
- `item_fts_tri`：`tokenize='trigram'`，服务中文子串（≥3 字）。
- 查询路由：CJK 且长度 < 3 → `LIKE '%..%'`（限定在已筛会话子集 + `LIMIT`，或直接提示「至少输入 3 个字」）；否则走 `tri`；纯拉丁词走 `uni`；混合查询两者取并集后融合排序。
- 排序：`bm25(item_fts_*, w) + 0.15 * role_boost(user) + 0.1 * recency_decay + phrase_boost`。
- 未来向量检索：`sqlite-vec` 的 `vec0` 虚拟表，存 item 级 embedding（`bge-m3` 本地 ONNX 或用户 API），**与 FTS 结果做 RRF 融合**，作为可选模块。

## 5. 数据库 Schema

> 设计原则：① 原始层不在此库（在 `raw/`）；② 所有时间戳为 `INTEGER ms UTC`；③ 一切可重建的派生数据（FTS）不进迁移脚本，由 `reindex` 命令生成；④ 删除会话走软删除 + `vacuum` 命令。

### FTS 表（由 `reindex` 生成，不参与业务迁移）

```sql
-- 英文/拉丁：词干 + 去音标
CREATE VIRTUAL TABLE item_fts_uni USING fts5(
  text, tool_name, content='item', content_rowid='id',
  tokenize='unicode61 remove_diacritics 2'
);
-- 中日韩：子串（≥3 字）
CREATE VIRTUAL TABLE item_fts_tri USING fts5(
  text, content='item', content_rowid='id', tokenize='trigram'
);
-- 标题单独一张（短文本，两套 tokenizer 各一列不方便，直接双表）
CREATE VIRTUAL TABLE conv_fts_tri USING fts5(
  title, content='conversation', content_rowid='id', tokenize='trigram'
);

-- 同步触发器（示例，uni 表同样处理）
CREATE TRIGGER item_ai AFTER INSERT ON item BEGIN
  INSERT INTO item_fts_tri(rowid, text) VALUES (new.id, new.text);
END;
CREATE TRIGGER item_ad AFTER DELETE ON item BEGIN
  INSERT INTO item_fts_tri(item_fts_tri, rowid, text) VALUES('delete', old.id, old.text);
END;
CREATE TRIGGER item_au AFTER UPDATE ON item BEGIN
  INSERT INTO item_fts_tri(item_fts_tri, rowid, text) VALUES('delete', old.id, old.text);
  INSERT INTO item_fts_tri(rowid, text) VALUES (new.id, new.text);
END;
```

> 备选（若双索引体积不可接受）：自定义 bigram 分词 → 与 `unicode61` 搭配，查询改写成 bigram 的 `AND` 短语。代价是索引器要自己实现，收益是单索引同时满足中英文。**建议先用双索引，按真实数据的 `dbstat` 结果再优化。**

## 6. 导入流水线

### 6.1 六步

```
①stage   原始层：解压/复制 → raw/<provider>/<sha256前缀>/<文件名>，算 sha256，写 import_file
②probe   adapter.probe() 命中 → 记 adapter_id/version；不命中 → 走 generic + 告警
③parse   并行（默认 4 并发，可配）→ ConversationDraft[]（内存有上限，超阈值落临时表）
④validate 结构校验 + 修复（孤儿节点、坏时间、重复 id）→ 告警进报告
⑤dedupe   四级匹配 → 命中则走 merge，不命中则新建
⑥commit  事务写 conversation/item/block/blob，更新统计与 FTS，写 batch 报告
```

**幂等性保证**：`import_batch(provider, kind, source_sha256)` 唯一 → 同一文件重复导入直接返回「已导入，无变化」；会话级再用 `(provider, external_id)` 与 `content_hash` 双保险。

**断点续传**：`plan()` 产出的任务 id 稳定（`sha256(path#entry#offset)`），重跑只补未完成任务。

### 6.2 哈希规范（决定查重质量）

| 层级 | 输入 | 目的 |
|---|---|---|
| 文件 | 原始字节 sha256 | 包级幂等 |
| Blob | 二进制 sha256 | 媒体去重 |
| **Item（语义哈希）** | `role \| kind \| tool_name \| normalize(texts…)` | 跨导出的消息级对齐 |
| 会话 | 排序后 item 哈希列表的 Merkle 根 | 会话内容等价判定 |
| 指纹 | MinHash(128) over item 哈希集合 | 近似重复（标题改了/顺序变了也能认出） |

`normalize(text)` 只做**无语义损失**的处理：

```
1. \r\n → \n；行尾空白去除
2. 连续空行折叠（≥3 → 2）
3. 去 ANSI 转义序列（终端输出）
4. Unicode NFC 归一化；全角空格→半角
5. 剔除「易变前缀」：时间戳括号、"当前时间: ..." 行
```

**不做**的事（会造成误判）：不改写绝对路径、不删除数字、不截断长文本、不跨语言翻译。

### 6.3 合并策略

| 情形 | 处理 |
|---|---|
| 完全相同（会话 content_hash 相等） | 仅更新 `last_batch_id`、`exported_at`，`stats.identical++` |
| 源是旧版本的超集（item 集合 ⊃ 已有） | 追加新 item，`revision++`，重算指纹 |
| 存在「同 id 但内容不同」的 item（用户编辑过消息 / provider 后处理） | 保留两版：旧 item 置 `is_active_branch=0` 并标记 `superseded_by`；`diff_json` 记录；订阅提示 |
| 无 `external_id`，但指纹相似度 ≥0.9 | 自动合并为同一会话（记 `reason='fingerprint'`） |
| 相似度 0.75–0.9 | 进 `dedupe_candidate`，UI「疑似重复」双栏对比，人工裁决 |
| 相似度 <0.75 | 视为不同会话 |

> **不做「按标题去重」**：用户大量存在「新建对话」重名；标题只能作为候选生成的特征之一。

## 7. 校验（Integrity Report）

用户要求「支持对话数据查重、校验」。校验分两类：

### 7.1 结构完整性（自动，导入时生成）

| 检查项 | 判定 | 处理 |
|---|---|---|
| JSON 解析失败 | 逐行/逐条目 | 记 `parse_error`，跳过不中断 |
| 孤儿节点 | `parent_id` 指向不存在 | 挂到根，`warn` |
| 环 | 拓扑排序失败 | 断边，`error` |
| 重复 `external_id` | 同批次内 | 合并取并集，`warn` |
| 缺失 blob | 引用存在文件不存在 | `orphan_ref`，UI 显示占位 |
| 孤儿 blob | 文件无引用 | 保留（可能来自分享/其他会话），`info` |
| 时间异常 | `updated_at < created_at`、时间在 2030 年后、时间戳为 0 | `warn` 并标记 `time_suspect` |
| 截断 | JSONL 尾行不完整 / zip CRC 失败 | `error`，标记会话 `partial` |
| 编码 | 非 UTF-8 / 含替换字符 U+FFFD | `warn` |
| 覆盖度 | 包内有 manifest 时，`conversations` 数量与 manifest 声明是否一致 | `error`（防「导出不完整」） |
| 附件完整度 | Claude 类只有 `extracted_content` 无原件 | `info: extracted_only` |

### 7.2 增量一致性（多次导出之间）

导入第 N 次导出时自动产出**差异报告**：

```
批次 A（2026-03-01，1,842 会话） vs 批次 B（2026-11-01，1,901 会话）
  + 新增会话        63
  ~ 内容增长        512   （典型：继续聊过的会话）
  ! 内容缩短        7     （⚠ 删除过消息 / 分支被裁剪）
  - 消失会话        4     （⚠ provider 侧已删除；本地保留，标记 "上游已删除"）
  = 完全一致        1,320
  ？ 疑似重复       12    （待人工裁决）
```

**「内容缩短」是最有价值的一条**：它正是「注销账号前我要确认我没有漏掉任何数据」的判断依据。UI 上要能一键列出这些会话。

### 7.3 报告产物

`import_batch.report_json` + 可导出 `verify-report.md`（人类可读）与 `verify-report.json`（机器可读），字段稳定、可版本对比。

## 8. 媒体处理

| 阶段 | 做法 |
|---|---|
| 识别 | 扩展名优先，其次魔数（`file-type`）；`.dat` 一律嗅探 |
| 外置 | JSON 中 `data:image/...;base64,` 与超阈值（>32 KB）的 `item_json` → 解出二进制 → sha256 → 去重入 `blobs/`；DB 留 `blob_id` / `payload_ref` |
| 缩略图 | `sharp` 生成 256/1024 两档 webp，作为独立 blob（`role='thumbnail'`） |
| 播放 | 音视频用 HTML5 `<audio>/<video>`，`Range` 请求由 server 支持；时长缺则 UI 不展示 |
| 权限 | 通过自定义协议 `sm://blob/<sha256>` 由 server 校验 token 后流式返回，**不暴露文件系统路径** |
| 导出 | 「导出为文件夹/HTML/Markdown + 媒体」时保持引用关系；HTML 导出为单文件时媒体转 data URI（可选） |

体积控制经验值（基于本机 Codex 数据）：45,231 items 中，`imageGeneration` 3 条即占 ~9 MB，`mcpToolCall`/`commandExecution` 占大头 → **不做外置的话，DB 会在几万条量级就变成几百 MB 的「不可备份巨石」**。

## 9. 性能预算

| 场景 | 目标 | 手段 |
|---|---|---|
| 启动到可浏览 | < 1.5 s | 只查 `conversation` 摘要字段；列表分页 |
| 会话列表滚动 | 60 fps @ 50k 行 | 虚拟列表 + keyset 分页（`updated_at,id`） |
| 打开对话 | < 300 ms | 单会话 item 一次取完（通常 <5k 行），前端树重建 |
| 全文检索 | < 300 ms @ 10 万 item | FTS5 + `LIMIT 50` + 结果只取 snippet |
| 导入 1 GB 导出包 | < 3 min | 4 并发解析 + 批量事务（500 条/批）+ `synchronous=NORMAL` |
| 重建索引 | < 2 min @ 10 万 item | 关闭触发器 → 批量 `INSERT INTO fts(fts) VALUES('rebuild')` |
| 内存峰值 | < 1.5 GB | 流式解析 + 大对象外置 + 背压 |

## 10. 安全与隐私

- **绑定** `127.0.0.1`，随机端口，每次启动生成一次性 token；`BrowserWindow` 带 token 加载，API 校验 `Origin` 与 token（防本机恶意网页 CSRF）。
- **零遥测**；崩溃日志默认本地，脱敏后可选上报（默认关）。
- **敏感字段**：`user.json`/`users.json` 里的邮箱、手机号入库但默认遮蔽（`ui_redact=1`），导出报告时自动脱敏。
- **加密（v2 可选）**：SQLCipher（`better-sqlite3-multiple-ciphers`）或整库文件放 VeraCrypt 卷；v1 只做「提示用户把库放在加密盘」。
- **只读原始层**：`raw/` 目录权限由程序设置为只读（Windows 上设置 ACL 比较重，改为「程序不写 + 启动时校验哈希」）。
