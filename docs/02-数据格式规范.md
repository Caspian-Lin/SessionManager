# 02 · 数据格式规范与适配器契约

本文档回答「每种来源到底长什么样、怎么映射、哪里有坑」。标注含义：
**[实测]** = 在开发机真实数据上验证过；**[文档]** = 来自官方帮助/第三方逆向文档，尚未用真实文件校验；**[待验]** = 需用户提供一份真实导出后确认。

---

## 1. 核心思路：多态原生会话类型 + 统一行为接口

不同来源的会话结构天生异构，且**查重与演化校验几乎全部发生在同一 `provider` 内部**（例如比较 3 月与 11 月两次 ChatGPT 导出、或追踪同一条 Codex rollout 增量追加），并不需要先把所有数据强制重编码成一种「通用中间 JSON 规范（OCA）」。

参考 `cc-switch` 等直接读取本地原生会话并统一展示的思路，本系统采用 **「保留原生类型 + 多态实现统一接口 + 按需投影 ViewModel」** 的设计：

```
NativeRaw (OpenAI mapping / Claude tree / Codex JSONL / DSH chunks / ...)
   │
   ▼  Adapter<TRaw>.parse()
SessionDocument<TRaw>  ── 统一行为接口（不同 provider 各自实现下列方法）
   ├─ validate()            原生字段与结构自检
   ├─ getMeta()             提取归属与指纹元数据 (provider, external_id, raw_format, head_hash, content_hash, fingerprint)
   ├─ diffWith(older)       同源增量增长 / 缩水截断告警
   ├─ extractSearchChunks() 抽取 FTS5 索引文本与 tool_name 切片
   ├─ toViewModel()         按需投影为 ConversationViewModel（供 UI / Markdown 展示）
   └─ toNativeJson()        序列化原生数据载体，零转换损毁落盘
```

四个核心抽象视角（而非跨源强制统一 JSON）：

| 抽象概念 | 语义 | 关键字段 / 职责 |
|---|---|---|
| `SessionDocument<TRaw>` | 一个原生会话的强类型封装 | 持有强类型 `rawData: TRaw`（按需外部落盘/切片）、`provider`、`rawFormat`、`externalId`，并实现统一校验、哈希、检索与投影方法 |
| `ViewNode` (`item` 表切片) | 展示/检索树上的节点投影 | `parent_id`、`role`、`kind`、`ordinal`、`created_at`、`tool_name`、`blocks_json`、`content_hash`、`is_synthetic` |
| `ViewBlock` (`blocks_json`) | `ViewNode` 内部的内容块 | `type` (`text/thinking/tool_use/tool_result/image/audio/file/code/citation`)、`text`、`blob_sha256`、`lang`、`tool_name` |
| `BlobAsset` (`blob` 表) | 内容寻址的二进制资产 | `sha256`、`mime`、`bytes`、`width/height/duration`、`origin_kind` |

**为什么投影树仍然保留 `parent_id`**：OpenAI 的 `mapping`、Claude Code 的 `parentUuid`、DSH 的 `agent/inbox/spliced` 都是图结构。强行拍平成数组会（a）丢掉 regenerate 的旁支，（b）让「这条消息从哪来」不可回答。投影到 `ViewNode` 时通过 `is_active_branch` 标记当前主干，UI 可切换分支。

**为什么区分 `is_synthetic`**：Agent 轨迹里混着大量非人写内容——审批策略变更注入（`agent/inbox/spliced`）、系统提示、压缩摘要（`compaction/summary`）、子 Agent 汇报。它们必须可见但默认折叠，否则会话不可读，也会污染搜索与记忆抽取。

## 2. OpenAI 网页端导出（`openai-web`）

**[文档]** 官方入口：<https://help.openai.com/en/articles/7260999-how-do-i-export-my-chatgpt-history-and-data>

### 2.1 包内布局（不能假设文件名）

| 文件 | 作用 | 处理 |
|---|---|---|
| `conversations.json` **或** `conversations-000.json`, `-001`, … | 会话正文，按体量**分片** | 两轮：按 `conversations*.json` glob 全收，逐个流式解析 |
| `shared_conversations.json` | 分享出去的会话 | 单独标记 `flags.shared=true`，默认不重复入库 |
| `message_feedback.json` | 点赞/点踩 | 映射为 `item.meta.feedback` |
| `tool_messages.json` | 工具相关响应 | 尝试并入对应 `tool_result` |
| `user.json` / `user_settings.json` / `export_manifest.json` | 账号、设置、清单 | **只读用于审计与账号归属**，不进检索；含 PII，UI 默认遮蔽 |
| `chat.html` | 全量 HTML 兜底视图 | 兜底通道：JSON 缺失/损坏时按 DOM 解析 |
| `*.dat` / `*.png` / `*.jpg` | 附件与生成图，**`.dat` 是无扩展名的裸文件** | 魔数嗅探 → `file-type` 判定 → `blob` |

### 2.2 会话对象与映射

```jsonc
{
  "id": "...", "conversation_id": "...", "title": "...",
  "create_time": 1712345678.9, "update_time": 1712345999.1,
  "current_node": "uuid", "default_model_slug": "gpt-4o",
  "is_archived": false, "is_starred": false,
  "mapping": { "uuid": { "id": "...", "parent": "uuid|null", "children": ["uuid"],
                         "message": { /* 见下 */ } } }
}
```

| 源字段 | 归一化 | 说明 |
|---|---|---|
| `conversation_id` \| `id` | `Conversation.external_id` | 优先 `conversation_id` |
| `create_time` / `update_time` | `created_at` / `updated_at` | **浮点秒**，×1000 转 ms |
| `title` | `title`，`title_source='provider'` | 空标题时取首条 user 正文前 40 字 |
| `default_model_slug` | `default_model` | |
| `mapping` | `Item[]` + `parent_id` | 从 `current_node` 回溯 → `is_active_branch=1`；其余分支保留但标记 |
| `message.author.role` | `Item.role` | `user/assistant/system/tool/critic` |
| `message.content.content_type` | `Block.type` | 见下表 |
| `message.create_time` | `Item.created_at` | 可为 `null`（继承父节点时间） |
| `message.recipient` | `Block.tool_name`（当为工具调用时） | |
| `message.metadata.model_slug` | `Item.model` | |
| `message.metadata.is_visually_hidden_from_conversation` | `Item.is_hidden` | 隐藏消息 |
| `message.metadata.is_user_system_message` | `Item.is_synthetic` | 注入的系统提示 |
| `message.metadata.user_context_message_data.{about_user_message,about_model_message}` | 未来 `memory` 表 | **导出的「记忆」就在这里**，且跨会话重复，需要去重 |
| `message.metadata.attachments[]` | `Blob` + `blocks_json` 引用 | 按 `file-service://file-xxx` ↔ `.dat` 对应，`blob_sha256` 关联 `blob` 表 |
| `message.metadata.citations` | `Block(type=citation)` | 联网检索引用 |

`content_type` → `Block.type`：

| content_type | Block.type | 备注 |
|---|---|---|
| `text` | `text` | `parts[]` 里可能是字符串或对象 |
| `multimodal_text` | `text` + `image` | parts 中的 `{content_type:'image_asset_pointer', asset_pointer:'file-service://…'}` |
| `code` | `code` | Canvas 代码 |
| `execution_output` | `tool_result` | 代码解释器输出 |
| `tether_browsing_display` / `tether_quote` | `citation` | 浏览结果 |
| `thoughts` | `thinking` | 思维链（部分账号有） |
| `reasoning_recap` | `thinking` | |
| `user_editable_context` / `model_editable_context` | `system_note` | 自定义指令、记忆快照 |
| `canvas` | `canvas` | 结构化文档 |

### 2.3 坑位清单

1. **单文件可达数百 MB、且是「一行 JSON」**：`JSON.parse` 会把 300 MB 膨胀到 1.5 GB+ 内存。必须用增量数组解析（`stream-json` / 自写 splitter：扫描顶层 `[`…`]` 的成员边界后逐项 `JSON.parse`）。
2. **分片不是固定 3 片**：以 `export_manifest.json` 或实际文件名为准，禁止硬编码。
3. **`mapping` 里存在孤儿节点**（`parent` 指向不存在 id）与环：用并查集建树，坏边挂到根并记入校验报告。
4. **`parts` 混类型**：字符串、`{type:'text'}`、`{content_type:'image_asset_pointer'}` 都可能出现，用判别式解析。
5. **`.dat` 无扩展名**：靠魔数（PNG `89 50 4E 47`、JPEG `FF D8`、WebP `RIFF..WEBP`、MP4 `ftyp`）＋ `file-service://` 引用名对齐；对不上号的标 `orphan_blob`。
6. **时间戳浮点、时区为 UTC 秒**：统一存 `INTEGER ms (UTC)`，展示层按本地时区渲染，并在 UI 显示导出时间与源时区。
7. **同一会话可能同时出现在 `conversations.json` 与 `shared_conversations.json`**：按 `external_id` 去重，配置取并集。
8. **隐藏消息承载了「记忆」与「运行时上下文」两类东西**：前者进记忆候选，后者（时区/当前日期/搜索指令）必须丢弃，否则记忆库会被噪声淹没。

## 3. Anthropic Claude 网页端导出（`anthropic-web`）

**[文档]** 借鉴 [Empirica 的实现说明](https://github.com/EmpiricaAI/empirica/blob/main/docs/reference/api/CLAUDE_AI_PARSER.md)，该文档明确记录了字段与偏差率。

### 3.1 包内布局

| 文件 | 作用 |
|---|---|
| `conversations.json` | 会话数组（可能很大，同样需流式） |
| `memories.json` | Claude 对你的记忆条目 `[{content, created_at}]` |
| `projects.json` | 项目与项目内文档 |
| `users.json` | 账号信息（PII，默认遮蔽） |

### 3.2 结构与映射

```jsonc
{
  "uuid": "abc123", "name": "标题", "created_at": "2026-01-15T10:30:00Z",
  "updated_at": "...", "account": { "uuid": "..." },
  "chat_messages": [{
    "uuid": "msg-1", "sender": "human",          // human | assistant
    "created_at": "...", "text": "降级后的纯文本",
    "content": [ {"type":"text","text":"..."},
                 {"type":"tool_use","name":"search","input":{}},
                 {"type":"tool_result","content":"..."},
                 {"type":"thinking","thinking":"..."} ],
    "attachments": [{"file_name":"...","file_type":"...","extracted_content":"..."}],
    "files": [{ "file_uuid": "...", "file_name": "..." }]
  }]
}
```

| 源字段 | 归一化 |
|---|---|
| `uuid` | `Conversation.external_id` |
| `name` | `title` |
| `created_at` / `updated_at` | ISO8601 → ms |
| `chat_messages[]` | 线性链：`item.parent_id = 上一条.id` |
| `sender: human` | `role='user'`（注意不是 `user`） |
| `content[]` | `Block[]`（**解析这个，不要用 `text`**） |
| `content[type=thinking].thinking` | `Block(type=thinking)` |
| `content[type=tool_use]` | `Block(type=tool_use, tool_name, tool_input_json)` |
| `content[type=tool_result]` | `Block(type=tool_result)` |
| `attachments[].extracted_content` | `Block(type=file, text=extracted_content)`（PDF/文本抽取结果） |
| `files[]` | `Blob` 引用（注意导出包**不一定含原件**） |

### 3.3 坑位

1. **`text` 与 `content` 不一致**：第三方实测 654 条里 87 条不同（13%），`text` 丢弃 tool 块与 thinking。→ 只信 `content[]`；`text` 仅作 fallback 与「差异告警」。
2. **`sender` 枚举是 `human`/`assistant`**，别按 `user` 匹配。
3. `chat_messages` 是**线性数组**，没有 parent 指针，但 `attachments`/重生成的历史仍需按时间排序；同一秒内多条时按数组顺序。
4. `memories.json` 是「当前记忆快照」，不是历史；重复导出会覆盖式变化 → 必须存为**版本化记忆**而不是覆盖。
5. 附件原件常常缺失（只有 `extracted_content` 文本）→ 校验报告里区分 `attachment_missing` 与 `attachment_extracted_only`。

## 4. DeepSeek 网页端导出（`deepseek-web`）

**[文档]** 官方 FAQ 明确存在导出功能：**「设置 → 数据管理 → 导出所有历史对话」**，导出内容「包含账号信息及所有历史对话」，下载链接 **7 天有效**。<https://static.deepseek.com/faq/index.html?lang=zh#/category/2>

**[待验]** 具体 JSON 结构未公开。这是本项目**唯一必须靠真实样本反推**的适配器。

### 4.1 应对策略：探针优先

不猜结构，先做一个「结构学习器」：

1. 解压 → 列出全部条目（文件名、大小、前 4 KB 嗅探）。
2. 在**找到的第一个 JSON 数组**上做形状推断：抽样 50 个元素，输出每个键的出现率与类型分布；识别候选 `messages` 数组（判定：元素含 `role|sender` 与 `content|text` 字段）。
3. 与已知指纹比对，命中即套用对应版本适配器；未命中则生成 `probe-report.json`（含脱敏 schema 摘要），用户可一键导出该报告来补适配器——**不需要上传正文**。
4. 兜底通道：③ 浏览器扩展导出的 JSON（`DeepSeek Chat Exporter`、`AI Exporter`、`ExportyAI` 等格式各异）④ 单文件 HTML/Markdown 抓取。

### 4.2 已知的第三方格式（作为次级目标）

- 扩展导出的 JSON 常见形状：`[{title, create_time, messages:[{role, content, ...}]}]` 或 `{conversations:[...]}`。
- 该类文件一律走 `generic-json` 适配器（启发式角色/内容识别），并在 UI 标注「第三方格式，字段完整度未知」。

### 4.3 风险

DeepSeek 的导出可能**不包含** reasoning（思维链）与附件；若如此，适配器需明确告知「该来源不提供 X」，而不是静默留空。

## 5. OpenAI Codex 本地会话（`codex-local`）

**[实测]** 全部结论来自本机 `~/.codex`。

### 5.1 三种存储并存（都要支持）

| 存储 | 路径 | 规模（本机实测） | 定位 |
|---|---|---|---|
| rollout 日志 | `sessions/YYYY/MM/DD/rollout-<ts>-<uuid>.jsonl.zst` | **256 个文件 / 477.5 MB（压缩后）/ 234 个会话 / 1,995 条用户消息** | **可移植的原始轨迹**，跨机器可用 |
| 归档 | `archived_sessions/rollout-*.jsonl.zst` | 同上 | 用户归档的会话 |
| 主存储 | `thread_history_<n>.sqlite` | **331.8 MB / 203 会话 / 860 turns / 45,231 items** | 当前活跃，含 UI 需要的投影 |
| 索引 | `session_index.jsonl` | `{id, thread_name, updated_at}`，94 条 | **标题来源** |
| 输入历史 | `history.jsonl` | `{session_id, ts, text}`，184 行 | 用户输入（可补全 rollout 缺失） |
| 导入台账 | `external_agent_session_imports.json` | `{source_path, content_sha256, imported_thread_id, imported_at}` | 别家会话被导入的记录 |
| 附件 | `attachments/` | 粘贴文本等 | 媒体 |

**策略**：默认读 `thread_history_*.sqlite`（有标题、有 turn 状态、无需解压、可增量）；rollout 作为「原始保真层」与「跨机器迁移」通道。两者按 `thread_id` 对齐，不一致时以 rollout（append-only 事实）为准。

### 5.2 rollout 记录格式 **[实测]**

```jsonc
{"timestamp":"2026-06-13T16:44:08.612Z","ordinal":0,"type":"session_meta",
 "payload":{"session_id":"...","id":"...","cwd":"C:\\Windows\\System32",
            "originator":"Codex Desktop","cli_version":"0.140.x",
            "model_provider":"...","base_instructions":"<巨大系统提示>","history_mode":"..."}}
```

`type` 取值与处理：

| type | payload 关键字段 | 映射 |
|---|---|---|
| `session_meta` | `session_id/id/cwd/originator/cli_version/model_provider/base_instructions` | 会话元数据；`base_instructions` **不入库正文**（体积大、含大段模板），仅存 hash |
| `turn_context` | `turn_id/started_at/model_context_window/collaboration_mode_kind` | 新建 `Item(kind='turn_context', is_synthetic=1)`，或只存 `turn` 边界 |
| `response_item` | `role/content[]`（`payload.type='message'` 等） | 正文消息 |
| `event_msg` | `token_count` / `agent_message` / `turn_completed{last_agent_message,completed_at}` | 统计与去重校验（`last_agent_message` 可与 `response_item` 交叉验证） |

注意 `ordinal` 单调递增 —— 用它做幂等游标（`next_rollout_ordinal`，Codex 自己也是这么做的，见 `thread_history_projection_state`）。

### 5.3 SQLite 结构 **[实测]**

```sql
thread_items(thread_id, turn_id, item_id, rollout_ordinal, created_at_ms,
             item_json TEXT, item_type TEXT, updated_at_ordinal,
             started_at_ms, completed_at_ms)
thread_turns(thread_id, turn_id, status, started_at, completed_at, duration_ms,
             first_user_item_id, final_agent_item_id, root_turn_id, ...)
thread_history_projection_state(thread_id, next_rollout_byte_offset, next_rollout_ordinal)
```

`item_type` 实测分布（本机）与体积：

| item_type | 条数 | 平均字节 | 最大字节 |
|---|---|---|---|
| `reasoning` | 16,763 | 135 | 9 KB |
| `commandExecution` | 12,192 | 9,704 | **1.37 MB** |
| `agentMessage` | 8,227 | 536 | 14 KB |
| `fileChange` | 3,014 | 4,850 | **3.08 MB** |
| `mcpToolCall` | 1,879 | 74,305 | 1.05 MB |
| `userMessage` | 1,201 | 838 | 465 KB |
| `webSearch` | 640 | 4,503 | 19 KB |
| `imageGeneration` | 3 | **2,960,000** | 3.23 MB |
| `contextCompaction` / `subAgentActivity` / `collabAgentToolCall` / `imageView` / `sleep` | 少量 | 小 | — |

**直接推论（架构级）**：
1. `item_json` 平均被工具输出撑大 → **大于 32 KB 的 payload 必须外置到 blob 存储**，DB 里只留 `payload_ref` + 摘要，否则 45k items 就能吃掉 300 MB+，前端列表滚动与备份都会崩。
2. `imageGeneration` 的 3 MB 条目几乎肯定是**内联 base64** → 必须抽出来做内容寻址，顺带获得跨会话图片去重。
3. 工具输出是「对话的一部分」，但要默认折叠，并提供独立的「只看我/AI 说的话」过滤器。

### 5.4 坑位

- **编码是 zstd，但扩展名分 `.jsonl.zst`；且未来可能是多帧**。解码器必须容忍单帧/多帧/未压缩三种（按魔数 `28 B5 2F FD` 判定）。本机样本是单帧，Node 内置可用；但**不要假设永远单帧**。
- `payload.base_instructions` 可达数十 KB，且每个会话重复 → 只存 hash，搜索时排除。
- 会话可能同时存在于 `sessions/` 与 `archived_sessions/`（`thread_id` 相同）。
- `cwd` 落在 `C:\Windows\System32` 等异常目录，说明启动目录才是事实来源；按「项目」分组时用 `cwd` 但不信任其为业务项目。
- SQLite 可能处于 **WAL 模式且在写入中** → 必须以 `?immutable=1` 或只读+`busy_timeout` 打开，绝不能写。

## 6. Anthropic Claude Code 本地会话（`claude-code-local`）

**[实测-路径]** `~/.claude/projects/<编码后的工作目录>/<session-uuid>.jsonl`（编码规则把 `\` `/` `:` 替换为 `-`，例如 `C--Users-28491-Desktop-Lab-Foo`）。

**[文档]** 行格式（参考社区解析器与 [Claude Code 消息格式说明](https://github.com/microsoft/amplifier/blob/main/docs/claude-code-sessions/core/MESSAGE-FORMAT.md)）：

```jsonc
{"type":"user|assistant|system|summary","uuid":"...","parentUuid":"...|null",
 "sessionId":"...","cwd":"...","gitBranch":"...","timestamp":"ISO8601",
 "isSidechain":false,"userType":"external","version":"1.x",
 "message":{"role":"...","content":[ {"type":"text","text":"..."},
            {"type":"tool_use","id":"toolu_1","name":"Bash","input":{}},
            {"type":"tool_result","tool_use_id":"toolu_1","content":[...]},
            {"type":"thinking","thinking":"..."} ]}}
{"type":"summary","summary":"...","leafUuid":"..."}
```

映射与坑：
- `parentUuid` 直接给树 → `Item.parent_id`；`isSidechain=true` 是子 Agent（Task）轨迹，标 `flags.sidechain=1`，默认在同一会话内以「子线程」展示。
- 工具结果以 `type:"user"` + `content[type=tool_result]` 出现 → 不要当成用户说话（`role='tool'`）。
- `summary` 行不是消息，是压缩摘要锚点 → `Item(kind='compaction')`。
- 同一 `sessionId` 可跨文件续写（`--resume`）→ 按 `sessionId` 合并，按 `timestamp`+`uuid` 排序去重。
- 文件可能因崩溃而**尾行截断** → 解析器必须逐行 try/catch，坏行计入报告而不是整文件失败。

## 7. DeepSeek Harness 本地会话（`dsh-local`）

**[实测]** `~/.dsh/sessions/<编码 cwd>/<session-id>/session.v4.jsonl.zstd`（另可能有 `session.jsonl.zstd` 旧代）。

### 7.1 容器格式（关键坑）

文件是**「每次追加写入一个独立 zstd frame」**的拼接流。实测 5.6 MB 文件 → 解出 15.9 MB / 18,744 行，含 13+ 个 frame。

- Node 内置 `zlib.zstdDecompressSync` **只解第一帧**，遇到后续帧抛 `ZSTD_error_prefix_unknown`（`Unknown frame descriptor`）。
- 实测 `fzstd`（纯 JS、无原生依赖）可完整解出全部帧。
- 结论：**统一使用能处理连续帧的解码器**，并在单测里覆盖「单帧 / 多帧 / 未压缩」三种输入。

### 7.2 事件流格式 **[实测]**

每行 `{type, seq, time, data}`，`type` 是 `域/事件` 命名。实测出现的类型（节选）：

| 类别 | 事件 |
|---|---|
| 会话 | `session`(header: `id/version/createdAt/cwd/agentPreset/delegationDepth`)、`session/title`、`session/end-seed` |
| 配置 | `permission/preset`、`sandbox/mode`、`approval/policy`、`agent-preset/selected`、`command/run`、`command/done` |
| 轮次 | `turn/start`、`step/start`、`step/end`、`turn/end` |
| 输入 | `user/message`、`agent/inbox/spliced`（**注入的上下文，非用户输入**） |
| 输出流 | `assistant/chunk`、`reasoning-chunks`、`tool-call-chunks`、`text-chunks`（**增量，需聚合**） |
| 结果 | `assistant/message`、`tool/call`、`tool/result`、`tool/code-dispatch` |
| 其他 | `todo/write`、`compaction/start`、`compaction/summary`、`request/header`、`request/context` |

**解析要点**：
1. `*chunk*` 事件是**流式增量**，不是完整消息。必须按 `turn/step` + 增量顺序聚合，或**只取 `assistant/message` / `tool/call` 的最终形态**，用 chunk 做「流式回放」。推荐：以最终态入库，chunk 仅在需要「打字机回放」时保留（默认丢弃以省空间）。
2. `agent/inbox/spliced` 是系统注入（例：审批策略变更提示）→ `is_synthetic=1`，默认折叠。
3. `compaction/*` 是上下文压缩 → `Item(kind='compaction', is_synthetic=1)`，并把「压缩后丢失的原文仍在库中」这一点在 UI 体现（否则用户会以为对话丢了）。
4. `command/run` 记录用户执行的斜杠命令（`/permission` 等）→ 归为 `kind='notice'`，不参与记忆抽取。
5. 附件在 `~/.dsh/attachments/`，需按会话/消息关联。

## 8. 通用兜底（`generic-json` / `generic-md`）

用于第三方扩展导出、手工 Markdown、以及未来未知来源：

- **`generic-json`**：启发式在 JSON 中寻找「数组 of 对象，元素含 role/sender + content/text」，抽取为线性会话；无法识别的字段整体存入 `Item.payload_ref`（不丢数据）。
- **`generic-md`**：识别 `**User**` / `## Assistant` 等常见分隔约定；失败则整篇作为单个 `text` block。
- 两者都必须标注 `adapter='generic'` 与 `confidence`，并在 UI 明示「结构未知，可能不完整」。

## 9. 适配器契约与多态会话接口（TS）

```ts
export type ProviderId =
  | 'openai-web' | 'anthropic-web' | 'deepseek-web'
  | 'codex-local' | 'claude-code-local' | 'dsh-local'
  | 'generic-json' | 'generic-md';

export type SourceRef =
  | { kind: 'file'; path: string }        // zip / json / jsonl / zst
  | { kind: 'dir';  path: string }        // ~/.codex 之类的目录根
  | { kind: 'sqlite'; path: string };

export interface ProbeResult {
  adapterId: ProviderId;
  version: string;        // 'v2'   —— 数据版本，不是代码版本
  confidence: number;     // 0..1
  evidence: string[];     // ['conversations-000.json', 'mapping+current_node']
  entries: string[];      // 需要处理的包内条目
  warnings: string[];
}

/** 所有 provider 原生会话对象必须实现的统一行为接口 */
export interface SessionDocument<TRaw = unknown> {
  readonly provider: ProviderId;
  readonly rawFormat: string;             // e.g. 'openai-web@v2', 'codex-rollout@v1'
  readonly nativeData: TRaw;

  getMeta(): SessionMeta;
  validate(): IntegrityIssue[];
  diffWith(older: SessionDocument<TRaw>): SessionDiffResult;
  extractSearchChunks(): SearchChunk[];
  toViewModel(): ConversationViewModel;
  toNativeJson(): string;
}

export interface Adapter<TRaw = unknown> {
  readonly id: ProviderId;
  probe(src: SourceRef): Promise<ProbeResult | null>;
  /** 把一个大来源切成可并行、可断点续传的任务 */
  plan(src: SourceRef, probe: ProbeResult): AsyncIterable<ImportTask>;
  /** 单任务解析：解析成原生类型封装 SessionDocument<TRaw>[]，不做去重、不写库 */
  parse(task: ImportTask, ctx: ParseCtx): Promise<SessionDocument<TRaw>[]>;
}

export interface ImportTask {
  id: string;                 // 稳定 id：sha256(path#entry#offset)
  src: SourceRef;
  entry?: string;             // zip 内路径
  range?: [number, number];   // 分片/偏移
  estimatedBytes: number;
}

export interface ParseCtx {
  /** 原始层落盘（解压后的 entry 副本），返回其 sha256 与本地路径 */
  persistRaw(entry: string, bytes: Buffer | NodeJS.ReadableStream): Promise<{ sha256: string; path: string }>;
  /** 流式大 JSON 数组解析器，避免 JSON.parse 300MB */
  streamArray<T>(src: NodeJS.ReadableStream): AsyncIterable<T>;
  /** 大负载外置 */
  spill(payload: unknown): Promise<string /* blob ref */>;
  log(level: 'info' | 'warn', msg: string, extra?: unknown): void;
}
```

**分层纪律**（这是可维护性的关键）：

- 适配器**只做原生格式探测与强类型封装**，不写 SQL、不做去重、不认识 UI。
- 解析产出的 `SessionDocument<TRaw>` 通过各自实现的多态方法接入统一的 `validate → dedupe (getMeta/diffWith) → merge → extractSearchChunks / toViewModel → commit` 流水线（见 03 文档）。
- 各会话的原生原始载体由 `raw` / `blob` 完整留存（`raw_format` + `raw_blob_sha256`），保证**零转换信息损失**（随时可读回原生 JSON/JSONL 并重新切片索引）。

## 10. 版本漂移与测试

| 机制 | 做法 |
|---|---|
| 版本探测 | `probe()` 返回 `version`；同 provider 可注册多个版本适配器（`openai-web@v1`, `@v2`），按置信度降序尝试 |
| 结构学习 | 未知结构生成 `probe-report.json`（仅 schema 摘要 + 脱敏样例），供维护者新增适配器 |
| 夹具 | `fixtures/` 下**合成**最小样本（版权与隐私安全）+ 用户**显式授权**的脱敏真实样本 |
| 回归 | 每个适配器配 `SessionDocument.toViewModel()`「黄金输出」快照测试：`fixtures/openai/v2/input.zip` → `expected.json` |
| 监控 | 导入报告里统计「未识别字段占比」；某字段突然飙升 = provider 改版信号 |

> 目标：**新增一个网页导出适配器 ≤ 0.5–1 人日**（无需维护独立中间 Schema 映射与跨语言生成，直接实现 `SessionDocument<TRaw>` 接口即可）。
